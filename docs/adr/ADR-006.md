# ADR-006: Production execution dual-control with configurable auto-confirm

**Status**: Accepted (implemented; SYSTEM confirm channel follows D16 directed-channel design, not state-funnel bypass)

**Date**: 2026-09-06 (spec rev.2, D12); implemented Phases 4, 7

## Context

CloudDM's existing ticket flow always passes through `WAIT_APPROVAL → (approval) → WAIT_CONFIRM → (manual confirm) → execution`. Even with an Internal approval template, a human must click "confirm execution" after approval. For PRE environments where the entire pipeline is automated (D7: PRE default fully auto), this manual confirmation step breaks the "rule audit passes → system auto-executes" contract.

For PROD, the question is whether confirmation should always be manual or can be automated — and in both cases, what guarantees that the Guard+Preflight still run.

## Decision

Adopt **D12: dual-control with configurable auto-confirm**:

1. **Default: manual confirmation** — after approval passes, a user holding `RDP_WORKER_ORDER_EXECUTE` (DBA-only) clicks "confirm execution" on the platform. This triggers the pre-execution Guard+Preflight. The result is "DingTalk approval + platform execution confirmation" dual-control.

2. **Configurable: `GOV_AUTO_CONFIRM=on`** — when this env param is set, the governance promoter (duty 5 of `GovPipelineScheduler`) automatically calls `confirmTicketBySystem` after approval passes. The auto-confirm path passes through the *same* Guard+Preflight as the manual path — no bypass exists.

3. **Config injection is governance-owned (D15)** — `autoExecConfig` is built server-side by the governance layer, not by the confirmer: pure DML → `enableTransactional=true`; DDL/MIXED → `false`; `errorStrategy=NONE` always. The confirmer (human or SYSTEM) cannot change it; gate-two G6 re-validates config compliance.

### SYSTEM directed channel (D16)

Phase 0 verification (§13-2) confirmed that `approvalTicket` (Service-layer hard-check: uid in `dm_approval_person`) and `confirmTicket` (`checkJobOperationEnable` hard-check: confirmer identity) cannot be bypassed by a "SYSTEM" user walking the normal funnel. The solution is a **directed channel**, not a state-machine bypass:

- **Approval**: imitates the third-party callback precedent (`ApprovalProviderServiceImpl.refreshApprovalStatus` directly calls `handler.approvalApproved()`). Context is never null (null silently drops the operator trail; `refreshApprovalStatus` passes null but the promoter must not). Operator = "SYSTEM" in `execUserName`.
- **Confirm**: `confirmTicketBySystem(ticketId, autoExecConfig)` — a copy of `confirmTicketInTransaction`/`prepareExecJobAsync` with exactly three deltas: identity checks removed (`checkJobOperationEnable` ×2), `queryByUid` → hardcoded `SYSTEM_OPERATOR`, naming. State-machine checks and every branch preserved verbatim; the original `confirmTicket` chain is zero-diff. The SYSTEM-copy gets the identical guard insertion as the original — the auto-confirm path has no bypass.

## Consequences

**Positive**:
- PRE environments achieve full automation (rule audit → auto-approve → auto-confirm → auto-execute → freeze) while PROD retains mandatory human confirmation by default.
- Both paths are Guard-gated; there is no execution route that skips Preflight or hash re-verification.
- The SYSTEM channel is a directed copy of existing code paths — it does not introduce a new state-machine path or a new user record (there is NO SYSTEM user in `dm_approval_person`; any path calling `queryByUid("SYSTEM")` NPEs).

**Negative / constraint**:
- The directed channel is a code copy (`confirmTicketBySystem`) — it must be kept in sync with `confirmTicket` if the original changes. The three deltas (identity removal, SYSTEM_OPERATOR, naming) are explicitly documented; any future divergence from the original's state-machine checks would break the safety guarantee.
- `GOV_AUTO_CONFIRM` defaults to off; PROD environments must explicitly opt in.
- There is no SYSTEM user record; the promoter must never call `queryByUid("SYSTEM")`.
