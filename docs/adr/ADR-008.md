# ADR-008: Guard dual entry points with scan-based self-healing promoter

**Status**: Accepted (implemented; touchpoint #3 disposal corrected from markJobFailedIfActive to doDeleteJob during implementation)

**Date**: 2026-09-06 (spec rev.2); implemented Phases 4, 7

## Context

The governance Guard must run at execution time to re-verify: promotion status, whole-ticket + per-statement hash, binding snapshot, Preflight, execution_key, and config compliance. But execution has two entry points in the existing engine:

1. `prepareExecJobAsync` (first execution — triggered by `confirmTicket`).
2. `dispatchJob` (retry / re-schedule — triggered by `retryAutoExecJob` or `AutoExecScheduleService.scanPendingJob`).

If the Guard only hooks `prepareExecJobAsync`, a retried or re-scheduled job bypasses re-verification. If the Guard hooks both but DENY logic is invasive (e.g. calling `markJobFailedIfActive`), it can corrupt the state machine or leave orphan jobs that block future creation.

Separately, the governance promoter (system auto-advance, revision freeze, status sync, failure notification, auto-confirm) must not race with the existing `ApprovalTaskScheduler` (1s loop) or directly write ticket status — doing so would break the state machine's single-owner invariant.

## Decision

Adopt **dual Guard entry points + scan-based self-healing promoter**:

1. **Touchpoint #2** (`prepareExecJobAsync`): guard runs at confirm time, before job creation. Config comes from the FO (not yet persisted). DENY → throw `ErrorMessageException(summary)` into the *existing* catch which already calls `restoreExecutionConfirmation`. Zero new disposal code. Both the original and the SYSTEM copy (`prepareExecJobAsSystemAsync`) get the identical guard insertion.

2. **Touchpoint #3** (`dispatchJob`): guard runs after `claimJobForPackaging` but before dispatch. Config comes from `job.getConfig()` (persisted). Per-statement re-verification reads task rows by `exec_order↔idx`. DENY → **`doDeleteJob` + `restoreExecutionConfirmationByGuard`**, NOT `markJobFailedIfActive`.

3. **Promoter = `GovPipelineScheduler`**: a daemon (`while(true){doSchedule();safeSleep(1s)}`, Throwable-guarded, per-duty try-catch). It operates only through existing service funnels (never directly writes status). The funnel's internal state checks naturally serialize concurrent operations with `ApprovalTaskScheduler`. Scan-based = stateless + restart-self-healing.

4. **Layered applicability**: non-governance (`govRole==null`) and PRE tickets short-circuit to PASS with **zero governance-table queries** (`verify(never())` covers promotionMapper, revisionMapper, eventMapper). Full six-gate evaluation applies only to `govRole=PROD`.

### Rejected alternatives

- **Guard only at `prepareExecJobAsync`**: rejected — retry/re-schedule paths bypass verification.
- **`markJobFailedIfActive` as touchpoint #3 disposal**: rejected during implementation — `markJobFailedIfActive` leaves an orphan FAILED job whose `depend_on_biz_id` blocks the next `createJob` INSERT (`uk_exec_auto_job_depend_biz` UNIQUE). The user returns to WAIT_CONFIRM but re-confirm collides forever. `doDeleteJob` (tasks+job) frees the slot, matching the `prepareExecJobAsync` catch pattern (deleteJob→restore). At `dispatchJob`-DENY time the ticket is still WAIT_EXEC (`markExecutionDispatched` not yet called) — restore's `!=WAIT_EXEC → return` guard accepts it.
- **Promoter directly writing ticket status**: rejected — would break the state machine's single-owner invariant and race with `ApprovalTaskScheduler`. The promoter only calls existing service methods; status changes go through the funnel's conditional UPDATE.

## Consequences

**Positive**:
- Both first-execution and retry/re-schedule paths are Guard-gated; there is no execution route that skips re-verification.
- Non-governance tickets pay zero cost (no governance-table queries, no event writes).
- The promoter is crash-safe: it scans for work each cycle; if it dies and restarts, it simply resumes. No persistent scheduler state to corrupt.
- Six gates are sequential, first-DENY-stops — expensive Preflight network calls never run after a cheap gate denied.

**Negative / constraint**:
- Circular dependency: `ApprovalControlServiceImpl → AutoExecService` already exists; `AutoExecServiceImpl → ApprovalControlService` (for `restoreExecutionConfirmationByGuard`, a 1-line public delegate to the private original, zero logic copy) requires `@Lazy` injection.
- The promoter's scan reuses `listFinishedTicketIdList` / `listUnFinishTicketIdList` — these mapper methods must include the right ticket statuses (e.g. `listUnFinishTicketIdList` SQL includes `EXEC_FAIL` — no new mapper needed for failure notification).
- `confirmTicketBySystem` is a directed copy of `confirmTicket` — the guard insertion must be kept in sync across both paths.
