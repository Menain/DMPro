# ADR-004: Dialect-neutral hash contract for statement-level immutability

**Status**: Accepted (implemented as specified; no corrections)

**Date**: 2026-09-06 (spec rev.2, D10); implemented Phase 4

## Context

Governance requires byte-level immutability guarantees for frozen SQL: the whole-ticket hash (`sql_hash`) and per-statement hash (`stmt_hash`) in the revision manifest must be reproducible at execution time to detect any tampering. The system supports both MySQL and PostgreSQL (D10: both dialects enter P0).

CODE_DESIGN proposed `sql_hash = SHA256(normalized_sql)` where "normalized" means parser-level AST reconstruction — the SQL is parsed, the AST is normalized, and the canonical form is hashed. The problem: multi-dialect parsing depends on each dialect's ANTLR grammar being complete and round-trip-stable. PostgreSQL's grammar has edge cases (e.g. dollar-quoted strings, cast syntax variants); MySQL has its own quirks (backtick identifiers, charset hints). A hash that changes when the parser is upgraded, or when the same SQL is hashed under different dialect configs, breaks the immutability contract.

## Decision

Adopt **D10: dialect-neutral hash contract**:

```
normalize(sql): split by \r\n|\r|\n → per-line trim() → replaceAll("\\s+", " ") → drop empty lines → join with "\n"
hash(sql):      SHA-256(normalize(sql)) → lowercase hex (64 chars)
```

- **Byte-level freeze, zero rewriting**: the original SQL text is frozen verbatim in `revision.sql_text` / `stmt_version.stmt_text`. The hash is computed over the text with *deterministic whitespace normalization only* — no AST, no parser, no canonical form reconstruction.
- **Whole-ticket + per-statement dual layer**: `sql_hash` (whole ticket) and `stmt_hash` (per statement) use the *same* `GovSqlHashUtils` implementation. Whitespace-layout differences (indentation, line endings, trailing spaces) never change a hash.
- **Dialect-neutral**: the same SQL text produces the same SHA-256 under both MySQL and PostgreSQL configs. This is verified by `GovernanceDualDialectTest#sqlHash_sameText_bothDialects_producesSameHash`.

### Rejected alternatives

- **`normalized_sql` (parser AST reconstruction)**: CODE_DESIGN's original proposal. Rejected because multi-dialect grammar completeness risk is high and the benefit (canonical form) is low — whitespace normalization is sufficient for detecting tampering (any semantic change changes at least one non-whitespace character).

## Consequences

**Positive**:
- Hash computation is a pure string operation — no parser dependency, no grammar version coupling, no dialect plugin loading.
- The same `GovSqlHashUtils` serves both freeze-time (Phase 4) and re-verification (Phase 6 promote, Phase 7 gate-two) — single implementation, no drift.
- Whitespace-tolerant: reformatted SQL (indentation changed, line breaks adjusted) produces the same hash, avoiding false DENY on cosmetic differences.

**Negative / constraint**:
- Semantically equivalent but textually different SQL (e.g. `SELECT 1` vs `SELECT (1)`) produces different hashes. This is acceptable — the contract is *immutability* (detect changes), not *equivalence* (detect semantic duplicates). Equivalent-but-different SQL that passes PRE validation is a new version, not a hash match.
- `GovSqlHashUtils` is the ONLY hash implementation for governance. Phase 6 promote re-verification and Phase 7 gate-two re-hash MUST call it, never re-implement. The 12 unit tests pin the whitespace contract.
