# ADR-003: Dual-source gate model with path B DML-only constraint package

**Status**: Accepted (implemented; threshold tiering relocated from PRE_INIT to submit-time — see correction note)

**Date**: 2026-09-06 (spec rev.2); implemented Phases 6-8

## Context

CODE_DESIGN's original absolute prohibition was "PROD never accepts directly-entered SQL; no PRE_SUCCESS = no production." This blocks a legitimate enterprise scenario: data-correction DML where PRE and PROD data states are intentionally divergent (e.g. correcting a production-only data anomaly that cannot be reproduced in PRE). Forcing such cases through the full PRE→Revision→Promotion path adds no safety value — the PRE execution result is meaningless when the data states differ.

The question is how to open a controlled direct-to-PROD DML channel (path B) without creating a bypass that weakens the security baseline for all production changes.

## Decision

Adopt **D11: dual-source gate model**. Rewrite the security baseline from "PROD SQL must come from PRE" to:

> Any PROD-executed SQL must: come from a frozen Revision (execution-time whole-ticket + per-statement hash re-verification) + be attached to a Promotion (gate snapshot) + have per-statement manifest consistent with PRE validation results + be approved + pass Guard/Preflight + be idempotently executed. The only difference between paths is the *source gate set*:
> - **Path A**: source gate = PRE per-statement validation complete (all `pre_exec=SUCCESS`).
> - **Path B**: source gate = DML-only (parser behavior analysis) + `GOV_DML_DIRECT` enabled + dedicated permission label + EXPLAIN row-count threshold tiering + mandatory rollback SQL.

All other baselines (immutability, mandatory approval, non-bypassable, auditable) are identical across both paths. Path B is not a loophole; it is a governance path with a different source gate. **DDL never has a direct path. PROD never has an in-place correction path.**

### Rejected alternatives

- **Absolute prohibition on direct PROD SQL entry**: rejected because it forces meaningless PRE validation for data-correction scenarios where PRE/PROD divergence is the normal case, providing no safety benefit while blocking legitimate work.
- **Allowing DDL through path B**: explicitly excluded — DDL structural changes must always go through PRE validation first (path A).
- **Path B failure → in-place correction**: rejected (D14) — path B has no PRE to return to; failure requiring SQL changes means resubmitting a new path B ticket (new revision, new promotion, re-approval).

## Consequences

**Positive**:
- Data-correction teams get a controlled channel for legitimate PRE/PROD-divergent DML without weakening the production baseline.
- The 8-condition DENY matrix applies uniformly: path B non-DML or switch-off = DENY (condition #8), enforced at both submit time and gate level.
- Path B six-object single-transaction creation (ticket → stmt_version → revision → promotion → event → ticketInfo writeback) ensures atomicity — mid-transaction failure rolls back all objects.

**Negative / constraint**:
- Path B blind code-retry is safe (every attempt creates a fresh ticket with new bizId; only revision_code/promotion_code collisions can raise DuplicateKey) but differs from Phase 6's idempotent-collision check which promotes an *existing* revision.
- Path B revisions are excluded from `availableRevisions` twice over (manifest pre_exec=PENDING fails the success filter; consumed filter catches the already-created promotion).
- Gate-two G2 `parseManifest` extracts idx+stmt_hash only (ignores `pre_exec` — PENDING never denies); path B never calls `promote()` so gate-one's `pre_exec==SUCCESS` check is structurally bypassed.

### Implementation correction (spec → implementation)

**Threshold tiering relocated from PRE_INIT to submit time.** The spec §4.2 places row-count threshold evaluation in the PRE_INIT handler chain. This is structurally impossible: PreInit handlers run in *parallel* (ThreadPoolExecutor; `displayOrder` is display-only) and `AbstractPreInitHandler.handle` is final with no "stay non-terminal" option — a threshold handler would read `expectedAffectedRows` before `DmlExplainPreInitHandler` writes it (MySQL UPDATE/DELETE = the main danger case → block level silently never fires). Phase 8 therefore evaluates thresholds synchronously *before* the transaction in `directDmlSubmit` via `GovDmlRowEstimator` + `GovRowLimitConfig`. `>block` rejects with zero objects created; `warn<x≤block` sets `riskLevel=HIGH` into `gate_result` (Phase 9 form reads the structured field). Estimation failure never rejects submission (per-statement error → 0 + evidence).
