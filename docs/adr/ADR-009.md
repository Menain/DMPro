# ADR-009: Statement-level versioning and correction loop (three-tier model)

**Status**: Accepted (implemented; touchpoint #6 locked to `replaceTask` after Phase 0 verification)

**Date**: 2026-09-06 (spec rev.2, D14); implemented Phases 4, 5

## Context

The existing engine can only `retryJob` (replay failed tasks as-is) or `skipTask` (skip a failed statement and continue). There is no "correct this statement → version+1 → replace the execution task → resume from the failure point" capability. There is also no failure notification — the submitter discovers failures only by checking the platform.

CODE_DESIGN's earlier proposal was a "lineage new ticket + statement skip ledger" design: on failure, create a new ticket that skips already-succeeded statements, tracked by a skip ledger. This was rejected in D14 because it fragments the change history across multiple tickets and loses the statement-level execution trail within a single change.

The question is how to enable in-place statement correction within the same ticket, with version history, while preserving the engine's task-level execution semantics.

## Decision

Adopt **D14: three-tier model (ticket → statement version → Revision with manifest)**:

1. **`dm_db_change_stmt_version` table** — the single source of truth for "each SQL statement's execution state and correction history since submission". Per ticket × statement index × version (from 1, +1 on correction). Fields: `stmt_text`, `stmt_hash` (dialect-neutral), `source` (INITIAL/CORRECTION), `fail_reason`, `operator_uid`, `gmt_create`. Current statement set = max `stmt_version` per `stmt_index`.

2. **Revision `stmt_manifest`** — frozen snapshot: `[{idx, stmt_hash, version, pre_exec, corrected_from:[{version,hash,fail_reason}...]}]`. The manifest captures each statement's hash, version, and execution result at freeze time. Gate-one verifies the manifest per-statement; gate-two re-verifies per-statement hash against the manifest.

3. **PRE correction loop** (same ticket, notification-driven):
   - Statement fails (after pre-checks pass) → fail-fast stop → whole ticket `EXEC_FAIL` → DingTalk notification (statement locator + error + deep link `/ticket/{id}`) → submitter corrects the statement on the platform → version+1 (CORRECTION) + incremental audit (rule rejects → version does not advance) → **touchpoint #6 `replaceTask`** → `retryJob` breakpoint resume (succeeded statements not replayed) → loop until all succeed → freeze (manifest records final version + correction history per statement).

4. **PROD no in-place correction** (D14): notification mechanism is reused (entry points to a disposal page, not a correction form). Transient failure → `retryJob` (passes `dispatchJob` guard per-statement re-verification). SQL change needed → return to PRE correction loop → new Revision → re-approve → re-promote (original promotion records FAILED terminal). Path B failure → resubmit a new path B ticket (new revision/promotion/approval — path B has no PRE to return to). **Never auto-modify SQL, never auto-rollback.**

### Touchpoint #6: `replaceTask` (locked after Phase 0 verification, §13-1)

`AutoExecService.replaceTask(String bizId, long failedTaskId, String newExecSql)`:
- `bizId` = the TICKET bizId (same semantics as `retryJob`/`skipTask` via `requireJob`→`queryByDependOnBizId`).
- Accepts task status FAILED **or ROLLBACK** only.
- Old task → CANCELED; new row copies structural fields with `exec_order` REUSED, fresh `biz_id` (`DmTeamUtils.nextExecTaskBizId()`) + `query_id` (UUID), status WAIT_EXEC.
- Replay safety (SQL-verified): `retryTask` resets `{FAILED, ROLLBACK, WAIT_CONFIRM, EXECUTING}` → WAIT_EXEC; `create()` replay accepts `{WAIT_EXEC, FAILED, ROLLBACK}`. CANCELED never replays; WAIT_EXEC always does.

### Rejected alternatives

- **Lineage new ticket + skip ledger**: the pre-D14 design. Rejected because it fragments change history across tickets, loses the statement-level trail within one change, and the skip ledger is a new concept the engine does not support.
- **Direct `exec_sql` overwrite** (Phase 0 alternative b): rejected — in-place overwrite loses the version chain (no history of the failed version) and reuses `query_id` causing cross-statement interference. `replaceTask` (alternative a) creates a new task row with fresh `biz_id`/`query_id`, preserving both the failed (CANCELED) and corrected (WAIT_EXEC) rows.

## Consequences

**Positive**:
- Correction happens within the same ticket — change history is self-contained; the manifest captures the full correction trail per statement.
- `retryJob` breakpoint resume is engine-native: FINISH/CANCELED tasks are never replayed; only FAILED/ROLLBACK/WAIT_EXEC tasks are re-packaged.
- The failing task STAYS `FAILED` even in transactional mode (`transactionRollback` SQL only flips WAIT_CONFIRM/EXECUTING to ROLLBACK, never FAILED) — so `queryListByJobId(jobId, FAILED)` pinpoints the culprit. Error text lives in `dm_mon_biz_log` (dependOnBizId=task.bizId, AUTO_EXEC_TASK, ERROR) — the task table has no error column.
- Gate-two per-statement re-verification is the backstop against replacement-set drift: any tampered or stale task row is caught by hash comparison.

**Negative / constraint**:
- `correctStatement` auth triple: `ownerUid==uid ∧ EXEC_FAIL ∧ govRole=="PRE"` — PROD ticket calls are directly rejected. The behavior type of the new SQL must equal the re-derived type of the original `stmt_text` — blocks DDL smuggling into DML tickets.
- **Partial-failure idempotent guard**: a multi-step service (version insert → engine replace → job retry) must guard on the LATEST PERSISTENT STATE, not the final state. If `newSql` hash == current max version's `stmt_hash`, skip audit + version insert unconditionally, then complete only the missing steps (task already CANCELED → just retryJob; task still FAILED/ROLLBACK → replaceTask + retryJob). Guarding only on "everything done" duplicates version rows when a mid-step failed. (Real defect, caught in check.)
- Failure notification: `MsgSendSpi` supports plain text only (no templates/Markdown/cards) — message body is plain-text-assembled. Idempotency = `FAIL_NOTIFIED` event keyed by `eventData.taskBizId` (correction creates a new task with a new bizId → naturally re-notifies). Write the event ONLY when a send was actually attempted (messenger found) — writing it on skip would suppress retry after IM gets configured later.
