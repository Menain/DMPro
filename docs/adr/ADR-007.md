# ADR-007: PROD approval provider strategy — mandatory third-party, no self-approval

**Status**: Accepted (implemented; approval sync fallback confirmed zero-governance-code, not a Phase 9 deliverable)

**Date**: 2026-09-06 (spec rev.2.1, D16); implemented Phases 6, 9

## Context

PROD governance environments require approval (non-closable, D7). The question is which approval provider to use and whether to hard-code DingTalk.

The existing approval system supports multiple providers via `ApprovalProviderSpi` (Internal/DingTalk/Wechat/Feishu/Custom), with per-environment template binding (`SQL_TICKET_INFO`/`CHANGE_TICKET_INFO` env params → `EnvTicketMO{approvalType, templateName, templateId}`). Unconfigured environments default to Internal auto-template `PROC-SELFMAKE-000000001`.

For PROD governance, allowing Internal (self-approval by the platform operator) would collapse the dual-control: the same person who initiates a change could approve it themselves. CODE_DESIGN proposed hard-coding DingTalk, but that couples the platform to a specific vendor.

A second problem surfaced in Phase 0 (§13-7): `ChangeApprovalHandler.convertToChangeForm` — which builds the approval form for external providers — hard-depends on CI/CD's `changeId`/`changeOwnerUid` from `ticketInfo`. A governance PROD ticket routed through external approval would throw an exception because it has no CI/CD change reference. This is touchpoint #7 (D16).

## Decision

Adopt **provider-agnostic strategy with mandatory third-party enforcement**:

1. **No hard-coded DingTalk** — the platform does not couple to any specific vendor. The concrete provider (DingTalk/Feishu/Wechat/Custom) is determined by the environment's approval template configuration.

2. **PROD governance environments must configure an approval template with a third-party provider** — gate-one gate #7: env param `SQL_TICKET_INFO` → `openTicket && type not blank && type != "Internal" && !isDelete`. Unconfigured or Internal → DENY (spec §5.5 anti-self-approval). This prevents small teams from using Internal templates to self-approve PROD changes.

3. **Governance approval form via touchpoint #7** — `convertToChangeForm` gets a governance branch: when `ticketInfo` contains governance references (`govRole != null`), delegate to `GovChangeFormAssembler` which maps nine fields onto *existing* `ChangeForm` structure (zero structure extension to SDK/DingApiUtils/DingConstant/Provider/DingTalk template). When no governance reference, CI/CD original logic is byte-identical. Parse failure on `ticketInfo` → info=null fallback (governance detection must never be a new failure mode for CI/CD tickets).

4. **`riskLevel` is a structured field**, not a string-parsed value — Phase 8 writes `item.put("riskLevel", ...)` into `promotion.gate_result`'s Threshold gate item; Phase 9 reads `item.get("riskLevel")`. The `reason` string is display-only; never parse values out of reason strings.

### Rejected alternatives

- **Hard-code DingTalk**: rejected — couples the platform to a vendor. The per-environment template binding mechanism already exists and supports multiple providers.
- **New `RDP_DB_CHANGE_PROD_CONFIRM` permission label**: rejected (D16) — `ApprovalController.confirm` already uses `RDP_WORKER_ORDER_EXECUTE` (DBA-only); the label's semantics match the authorization matrix. Governance PROD's additional constraints (no-skip, etc.) are enforced by touchpoint #5, not a new confirm label.

## Consequences

**Positive**:
- Platform remains vendor-agnostic; DingTalk is the initial deployment but not architecturally required.
- Anti-self-approval is enforced structurally (gate #7), not by convention — no Internal template can reach PROD execution.
- CI/CD ticket approval form behavior is byte-identical (zero-diff below the governance branch); the assembler owns all governance-specific data-source injections.
- Approval sync fallback (Stream/HTTP-callback/getLastInfo) needs zero governance code: the callback chain has no `approBiz` filter (governance DM_CHANGE tickets are covered); duplicate-callback idempotency is two-layer (engine end-status checks + duty-4 conditional transit); the callback chain ends at WAIT_CONFIRM with no execution trigger (execution only via confirm→guard).

**Negative / constraint**:
- The `convertToChangeForm` branch is a touchpoint on existing CI/CD code — the branch must be maintained if the original method is refactored. The branch shape (parse→branch→delegate) is explicitly documented to keep this maintainable.
- Field-level null-safety (not PRE/PROD dual-branch): promotion-derived fields assemble only when `promotionId!=null`, revision-derived only when `revisionId!=null`, missing → "-" placeholder. `logicalDbId==null` (data corruption) → fail-fast business exception.
- The initial deployment requires a DingTalk approval template configured per PROD environment; this is a Phase 12 gray-release precheck item.
