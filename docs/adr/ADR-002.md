# ADR-002: Reuse dm_approval with a thin governance layer and weak coupling

**Status**: Accepted (implemented across Phases 2-9; touchpoint #7 added post-Phase-0 verification per D16)

**Date**: 2026-09-06 (spec rev.2.1); implemented Phases 2-9

## Context

CODE_DESIGN proposed three new tables — `db_change_ticket`, `db_change_execution`, `db_change_approval` — to carry governance tickets, execution records, and approval state. Code investigation of open-cdm 4.2.0 revealed that the existing `dm_approval` table already contains every field the governance layer needs: `rawSql`, `rollBackSql`, `envName`, `bindDsId`, `expectedAffectedRows`, `ticketInfo` (free JSON), `features` (enum), plus a complete state machine (`ApprovalStatus`: 15 states) and business type `ApprovalBiz` (DM_QUERY / DM_CHANGE / ...).

Building a parallel ticket system would duplicate the state machine, approval engine, execution dispatch, and all their edge cases. The question is how to attach governance semantics to existing tickets without modifying `dm_approval`'s table structure or the state machine.

## Decision

Adopt **D9: new governance-domain tables + weak coupling with the existing ticket system**:

1. **Governance tables hold the ticket id** (forward link, e.g. `dm_db_change_revision.source_ticket_id → dm_approval.id`). The governance layer owns its own state (promotion status machine, revision immutability, event timeline) without mirroring ticket status.

2. **`ticket_info` / `ApprovalMO` carries the reverse link** — governance writeback fields (`promotionId`, `revisionId`, `logicalDbId`, `govRole`) are added as POJO fields on `ApprovalMO`. This is the existing free-JSON slot (CI/CD already uses `changeId`/`changeOwnerUid` in it). No `dm_approval` column changes.

3. **`features` column is NOT used** — it is a pure enum (`ApprovalFeature`); inserting custom values would break Jackson deserialization. The `ticketInfo` JSON is the correct extension slot.

4. **Core touchpoint budget = 7 small hooks** (rev.2.1, D16 added #7 post-Phase-0):

| # | Touchpoint | Phase |
|---|---|---|
| 1 | `createSqlTicket` parameterize `approBiz` + `ApprovalMO` governance fields (POJO fields added first) | 4 |
| 2 | `prepareExecJobAsync` guard entry | 7 |
| 3 | `dispatchJob` guard entry | 7 |
| 4 | Revoke protection for `PERM_GROUP:`-marked rows | 2 |
| 5 | `skipTask`/`continueTask` PROD interception | 7 |
| 6 | `AutoExecService.replaceTask` (statement replacement) | 5 |
| 7 | `convertToChangeForm` governance branch | 9 |

Everything else is purely additive (new tables, new services, new controllers, new Flyway script, new frontend). The state machine, approval engine, DingTalk Provider, executor core, parser, and masking are not modified.

### Rejected alternatives

- **New `db_change_ticket` table**: deleted — `dm_approval` already carries rawSql/rollBackSql/expectedAffectedRows/envName/bindDsId and the full state machine.
- **New `db_change_execution` table + execution_key**: merged into `dm_db_change_promotion` (idempotency key moved up). Execution records are already carried by `dm_exec_auto_job/task` with `depend_on_biz_id` uniqueness (= one ticket, one job).
- **New `db_change_approval` table**: deleted — `ApprovalProviderSpi` + template/person tables + DingTalk Stream/callback sync are all production-ready.
- **`features` column as extension slot**: rejected (pure enum, breaks Jackson).
- **`console_job`/`console_task` handler concept**: does not exist — the real mechanism is `dm_exec_async_task` and `AutoExecService`.

## Consequences

**Positive**:
- Upstream CloudDM merge conflicts are bounded: only 7 hook points touch existing code; all governance tables are independent and weakly-linked.
- The existing state machine remains the single owner of ticket status; the governance layer never writes ticket status directly (promotion status is synced one-way from ticket terminal states).
- CI/CD (`dm_change_flow`, `ChangeActionForApproval`, frontend `views/cicd/`) has zero changes (D13).

**Negative / constraint**:
- Touchpoint #7 was discovered post-Phase-0: `ChangeApprovalHandler.convertToChangeForm` hard-depends on CI/CD's `changeId`/`changeOwnerUid` — governance PROD tickets routed through external approval would throw. This became a 7th touchpoint (originally budgeted 6).
- `ApprovalMO` POJO fields must be added *before* any governance writer (§13-9: `updateAutoExecFlag`/`restoreExecutionConfirmation` have read-modify-write paths that silently drop unknown fields if the POJO lacks them).
- The `approBiz=DM_CHANGE` parameterization touches only 2 hard-coded sites (`createSqlTicketInTransaction`); all downstream code (PreInit, handler routing, query display, frontend) already supports `DM_CHANGE` natively.
