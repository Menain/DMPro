# ADR-010: Execution config component routing — mixed tickets, no forced split, no SKIP

**Status**: Accepted (implemented as specified; no corrections)

**Date**: 2026-09-06 (spec rev.2, D15); implemented Phases 4, 7

## Context

The existing engine's `enableTransactional`/`errorStrategy` config (`RsExecAutoJobConfigObj` stored in `dm_exec_auto_job.config` JSON) is freely chosen at confirm time by whoever clicks "confirm execution". There is no dialect guard: **MySQL DDL statements implicitly commit and silently puncture transaction mode** — the engine has no protection (confirmed by code investigation, risk #11).

This means:
- A mixed DDL+DML ticket in transactional mode would have DDL implicitly commit mid-transaction, then if a later statement fails, the "rollback" would not roll back the DDL — leaving the database in a partially-applied state.
- `errorStrategy=SKIP` on a PROD ticket would allow skipping a failed statement, meaning the execution set differs from the approved set.

The question is how to enforce safe execution configuration without forcing users to split mixed tickets into separate ones (which fragments the change and adds overhead).

## Decision

Adopt **D15: component routing by parser behavior analysis**:

1. **Allow mixed tickets, no forced split** — the governance layer uses parser behavior analysis (`BehaviorAction`: CREATE/ALTER/DROP/INSERT/UPDATE/DELETE...) to classify each statement as DDL or DML, then aggregates the ticket's `change_type` (DDL / DML / MIXED). Mixed tickets are accepted; the config is routed by the aggregate type.

2. **Component routing table**:

| `change_type` | `enableTransactional` | `errorStrategy` | Rationale |
|---|---|---|---|
| Pure DML | `true` (whole-ticket one transaction; failure → full rollback, task→ROLLBACK) | `NONE` (fail-fast stop) | DML is transactionally rollback-safe; full-rollback semantics: all rows reset, correct for correction-loop re-run |
| Pure DDL | `false` (per-statement autocommit) | `NONE` (fail-fast stop) | DDL is physically non-rollback-safe; autocommit is the only safe mode |
| MIXED (DDL+DML) | `false` (per-statement autocommit) | `NONE` (fail-fast stop) | DDL component makes transactional mode unsafe; autocommit + fail-fast is the only consistent option |

3. **Governance tickets force `errorStrategy=NONE`** — a statement failure → locate the statement → whole ticket stops → return to submitter. No RETRY (in-place retry) for governance tickets.

4. **Governance PROD tickets forbid `SKIP`** — `errorStrategy` cannot be SKIP, AND `skipTask`/`continueTask` interfaces hard-block governance PROD tickets (touchpoint #5). Production execution set must = approval set.

5. **Config is governance-injected, confirmer-locked** — at PRE, the SYSTEM auto-advance writes `autoExecConfig` per D15. At PROD, the human confirmation UI locks the config; gate-two G6 re-validates job config against the component-routing table server-side regardless of what the client sends. The confirmer cannot change it.

### Rejected alternatives

- **Force splitting mixed tickets into separate DDL and DML tickets**: rejected (P0 explicitly excludes "工单自动拆分双单编排") — it fragments the change, adds approval overhead, and the governance layer can already identify components and route config without splitting. (Optional P1 candidate if needed.)
- **In-ticket segment transactions** (DDL segment autocommit + DML segment transactional): rejected (P0 explicitly excludes "工单内分段事务") — engine-level segment transaction control is a large change with low benefit; autocommit+NONE for all DDL-containing tickets is simpler and consistent.
- **Allow RETRY errorStrategy for governance tickets**: rejected — in-place retry of a failed statement without correction could retry a structurally broken statement indefinitely. The correction loop (D14) is the controlled retry mechanism (version+1 + audit + replaceTask).

## Consequences

**Positive**:
- Mixed DDL+DML changes proceed as a single ticket with a single approval, reducing overhead while maintaining safety.
- The MySQL DDL implicit-commit trap is guarded structurally: transactional mode is only available for pure-DML tickets (both dialects physically consistent — PG DDL is transactional but the guard is dialect-agnostic and conservative).
- Production execution set = approval set is enforced structurally (no-skip + touchpoint #5), not by convention.
- Config compliance is server-side verified (G6), not trusted from the client — §6.4 red line (frontend-sent `autoExecConfig` is re-validated, never trusted).

**Negative / constraint**:
- Pure-DML transactional failure means full rollback → correction re-runs all statements (ROLLBACK tasks replay). This is semantically correct (database state was zero-changed) but means more re-execution than autocommit mode. Accepted as the safe default.
- The `confirm` endpoint's FO carrying `enableTransactional`/`errorStrategy` per D15 is the EXISTING endpoint contract, NOT a §6.4 smuggle — G6 re-validates the config against the component-routing table server-side regardless of what the client sends.
- `GovPreInitGuardHandler` (displayOrder=0) runs a lightweight subset at approval time (promotion exists ∧ not terminal + whole-ticket hash + binding vs snapshot) — NO Preflight at approval time (expensive network calls deferred to gate-two).

## Implementation landing

- **Phase 4** (commit `330f1ef7`): `GovStmtSplitService` classifies per-statement DDL/DML via `BehaviorAction`; `preSubmit` writes `change_type` (DDL/DML/MIXED); `confirmTicketBySystem` injects D15 config (DML→`enableTransactional=true`; DDL/MIXED→`false`; `errorStrategy=NONE` always).
- **Phase 7** (commit `c96c1473`): gate-two G6 (config compliance: `errorStrategy=SKIP` always DENY + `enableTransactional` mismatch DENY); touchpoint #5 (`skipTask`/`continueTask` PROD interception); `GovPreInitGuardHandler` (lightweight subset, displayOrder=0).
- **Tests**: `GovExecutionGuardServiceImplTest#checkByTicket_configSkip_denyG6` + `checkByTicket_configTransactionalMismatch_denyG6`; `ApprovalControlSkipContinueTest` (4: skip + continue × PROD-rejected + non-gov-pass-through); `GovernanceDualDialectTest#preSubmit_mysql_configTransparentlyPassedToSplit` + `preSubmit_postgresql_configTransparentlyPassedToSplit` (D15 config values do not drift by dialect).
