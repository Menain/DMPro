# ADR-012: Approval callback round binding — flow consistency guard + approval_round (A+B), revising bridge PRD ruling #5

**Status**: Accepted (implemented 2026-10-11, task C5 `10-11-approval-round-binding`; user ruling "A+B 一步到位"). Delivery notes: guards ④FLOW_ID_MISMATCH/⑤ROUND_MISMATCH live in `applyExternalApprovalResult` (scope `meta != null ∧ External`, tolerant-first); migration `V202610110002__dm_approval_round` (slot after C4's V202610110001); `clearOutboundForNewRound` = round-increment; `flows/create.context.round` additive (null-safe fallback 1); FO/meta `externalRound` additive; empty-window observation = warn log + `identityBackfill` success-event marker; strict tier = root KV `govExternalCommandStrictFlow` (default false, code in place, reasons FLOW_ID_MISSING/ROUND_MISSING); O-C2-1 closed — execute/return guard rejections audit through the shared REQUIRES_NEW core (public command-named `appendRejectedCommandEvent`; execute reasons EXECUTE_STATUS_MISMATCH/CHANNEL_MISMATCH, return umbrella RETURN_GUARD — deliberate discretion: which of the five return preconditions fired is carried by ticketStatus + message + app log). Discretion per design M8: the audit core stayed on ApprovalProviderServiceImpl (no new component — injection edge already exists). Form C (eventId) not adopted per Decision 6. Bridge-side additive asks + strict-tier gray release → project-final unified integration test (manual `tests/governance/dingtalk_bridge.md` §5A).

**Date**: 2026-10-11

## Context

Inbound external approval commands (approve/reject/cancel via `/api/open/dbchange/*`, AK/SK-signed) carry an **optional** `externalFlowId` that is persisted to `dm_approval.appro_identity` *only when currently empty* — **no comparison, ever** (verification: research `p0-gap-verification.md` §B; design inputs `research/adr-b-round-binding-input.md`). Consequences at HEAD=be0f2f8c:

- A stale DingTalk flow's callback (F1) reaching a *new* approval row (A2, created by release resubmit with a stable `(bizType=RELEASE, bizId=releaseId)` key) passes all three state guards and **back-writes F1 into the empty identity**, approving the release with zero rejection or alarm; the return-path `flows/cancel(F1)` is best-effort and may have failed, leaving F1 alive bridge-side;
- Even a fully compliant bridge has an **identity-empty window**: §10.6 explicitly allows "events may arrive before the outbound response" — F1 events landing before F2's backfill still get accepted. Pure flowId comparison cannot close this window; only a round token can;
- Rejected commands had zero DB audit trail — **already fixed** by task C2 (commit be0f2f8c, `EXTERNAL_COMMAND_REJECTED` + REQUIRES_NEW);
- The bridge PRD ruling #5 had deliberately chosen "the external engine is the sole approval truth source; commands are facts; state guards + idempotence make replay/out-of-order harmless". The improvement plan (§2 P0-2) challenges that ruling's sufficiency — and the code facts confirm the challenge.
- Contract constraints: the inbound command surface is declared **behavior-frozen** (openapi-orchestration.md L5) and `externalFlowId` is optional by contract ("minimal call: ticketId only", §5.4 L235) — a *strict* "missing flowId → reject" mode would breach the frozen contract.

## Decision

1. **Bridge PRD ruling #5 is revised**: "external engine = sole approval truth source" is **retained**; the console upgrades from "state guards only" to **"state guards + flow consistency guards"**. The console still does not poll, reconcile, or own the approval lifecycle — it only refuses to act on commands that provably belong to a different flow/round.
2. **Flow consistency check (form A, console-only)**: for the three-state commands under `meta != null && approType == External`, if `externalFlowId` is non-blank **and** `appro_identity` is non-blank **and** they differ → reject with new reason `FLOW_ID_MISMATCH` via the C2 audit infrastructure (`appendRejectedCommandEvent`, REQUIRES_NEW, `EXTERNAL_COMMAND_REJECTED`). **Tolerant mode**: either side blank → current behavior (including the empty-identity first-writer-wins backfill), because strict mode would breach the frozen "ticketId-only" contract. Scope is strictly `meta != null ∧ External` — legacy direct channels (meta=null refresh path) are untouched per the §7.3 bit-identical promise. Misfire risk ≈ 0: D5 ticket-level resubmit never reaches the check (execute/return do not consume flowId; three-state commands are pre-rejected by the WAIT_APPROVAL guard), skipOutbound/pull-mode rows have empty identity.
3. **Explicit approval round (form B, integrated per user ruling)**: `dm_approval.approval_round int NOT NULL DEFAULT 1` (additive migration per `V202610090001` precedent); `clearOutboundForNewRound` becomes round-increment semantics (round+1 **and** identity/outbound-column reset); outbound `flows/create.context` carries the round additively; inbound commands may carry `externalRound` (additive optional FO field) — when present and mismatched → reject with reason `ROUND_MISMATCH` (+audit); when absent → skip (tolerant-first). A **strict tier** (missing round → reject once the bridge is confirmed upgraded) is deferred to a config flag because it collides with the §10.6 "events may precede the outbound response" boundary and must gray-release with integration-test evidence.
4. **Empty-window observation (interim mitigation for the §10.6 window)**: when a command's flowId is back-written into an empty identity, emit `log.warn` + an audit event trail, so the window's real-world frequency is measurable before the strict tier is ever considered.
5. **Bridge-side requirements (external project, additive)**: read `round` from `flows/create.context`, echo `externalRound` on inbound commands, keep honoring the round-2 "must return a new flowId after cancellation" hard requirement (§10.2 L492-495). `openapi-orchestration.md` revisions: §5.4 payload (+externalRound), §10.2 (+round semantics), the L5 inbound-freeze declaration (amended to "frozen except the additive FLOW_ID_MISMATCH/ROUND_MISMATCH rejections"). Bridge adaptation + strict-tier gray release are verified in the **project-final unified integration test** (user ruling 2026-10-11).
6. **eventId idempotence (form C) is NOT adopted now**: the state-guard already renders replay/out-of-order harmless (error-style, zero side effects); eventId's real increment (turning "retry hits guard error" into decidable idempotent success) does not include stale-round protection — an old flow's events carry fresh eventIds — so C alone would not close the target vulnerability, while hard-depending on the bridge generating retry-stable ids and touching the append-only event table (with the `AbstractUpgradeJavaMigration` 1062-ignored unique-index trap). Reconsider after integration-test evidence if the bridge's convergence logic needs it.

### Rejected alternatives

- **Form A only (flowId comparison, no round)**: leaves the identity-empty window open permanently (F1-before-F2 backfill accepted); the window is exactly the compliance-independent hole. Rejected by user ruling in favor of A+B.
- **Full form C (eventId dedup table/column)**: see Decision 6 — limited increment, hard bridge dependency, migration trap; deferred, not rejected forever.
- **Strict flowId mode (missing → reject) from day one**: breaches the frozen §5.4 "ticketId-only minimal call" contract and would break pull-mode/skipOutbound tenants; tolerant-first with observation is the compliant path.

- `ResubmitOutboundResetTest` / `DingBridgeOutboundServiceTest` pins update for round-increment semantics; `dm_approval` DO/XML additive column;

- Contract docs: openapi-orchestration.md §5.4/§10.2/L5 revisions; dingtalk_bridge.md integration manual gains round-binding scenarios for the final unified test;
