# ADR-013: Release-chain frozen plan routing — segment manifest carrier, freeze + capability-recheck semantics, staged DML_BATCH blocking, dedicated route override

**Status**: Accepted (2026-10-12, task C7 `10-12-release-chain-frozen-routing`; four user rulings via AskUserQuestion, 2026-10-12). Milestone cadence M1→M2→M3, each independently shippable and rollbackable. **M1 (carrier + freeze propagation, write-only) implemented 2026-10-12**: migration `V202610120001__prod_release_stmt_segment` (manifest table + additive `dm_prod_release_stmt.plan_hash`), merge-transaction propagation in createRelease/resubmit (`buildSegmentRows`/`propagateSegments` — lifecycle twin of the schema-snapshot table), the four cascade-delete paths (returnStmt / returnRelease / handleRejected / handleCancelled), `ReleasePlanHashUtils` canonical pin, NO stock backfill. M2 (segment-aware dispatch + GHOST executor wiring + DML_BATCH blocking + capability recheck) and M3 (plan-drift gate + route override + frontend review surface) are pending in the same task; the stage contract is pinned in `.trellis/spec/backend/governance-contracts.md` → "Release-chain frozen plan manifest".

**Date**: 2026-10-12

## Context

The ticket chain freezes threshold-exceeding DDL/DML into a segment plan (`precheck_result.segments`: GHOST / DML_BATCH / AUTOEXEC, 1-based global exec_order domain with holes) and dispatches it through `V2GroupDispatch` (segments → flags → legacy). The release chain, at merge, copies **only the sql_content text + its hash**: the plan degrades to display-only `gate_result` disclosure keys (`ghostRouted` / `dmlBatchRouted`), and `createReleaseStmtJob` always re-splits the frozen text into plain DIRECT tasks (evidence: read-only survey `research/c7-release-chain-survey.md` at HEAD=a9599a46; the code self-admits "release-chain ghost routing is M5"). Consequences:

- Governance strength depends on the **approval mode** (DIRECT vs VIA_RELEASE), not on risk: the same frozen DML enjoys throttled keyset batching on the ticket chain but replays as ONE direct statement through the release chain; a threshold-exceeding PRE_DDL ALTER that ran lock-free (gh-ost) on pre replays on prod as a plain locking ALTER;
- The hash gate is fail-closed but locks **text only** — executor, route, plan and parameters are outside the frozen comparison, so a downgrade-to-DIRECT is structurally undetectable;
- The internal improvement plan (`docs/governance/internal-db-platform-improvement-plan.md` §2, "PROD 执行计划" row) requires: revision/manifest/target-DB/executor/parameters all frozen; pre-release recheck then segment-by-segment execution per plan; unsupported capability → block or explicitly-approved risk, **never a silent downgrade**.

Structural facts that shape the carrier choice: a release stmt is 1:1 with its source group (one pair → one prod DS/DB), so per-DB plans map per-stmt naturally; the source plan is already reachable inside the merge transaction (`collectSourceEntries` carries the whole `DmTicketDbStmtDO` including `precheckResult`) but is persisted nowhere on the release side; `dm_prod_release_stmt_schema` is a proven isomorphic precedent (per-release-stmt companion table, merge-transaction propagate, cascade deletes on return/reject/cancel).

## Decision

1. **Carrier (ruling 1): option B — the standalone manifest table `dm_prod_release_stmt_segment`** keyed by `release_stmt_id` (1 stmt : N segments, `uk_rstmt_seg(release_stmt_id, seg_idx)`, redundant `release_id` for the cascade delete). Plan and runtime live in the SAME table (release chains have few segments and low write frequency; single-writer discipline = the existing release row lock) — but release-side orchestration gets a NEW `ReleaseSegmentService` (M2), never `TicketSegmentService`: the two chains' segment writers stay isolated. `dm_prod_release_stmt` gains ONE additive column `plan_hash varchar(64) NULL` as the stmt-level integrity pin; `executionKey` is untouched (execute-once idempotence key, no content/plan — red line).
2. **PRE_DDL ghost plan target-DB semantics (ruling 2): freeze + capability recheck.** The pre-side routing decision is reused frozen — no re-probe, no re-route; the frozen manifest is the single routing truth. At prod dispatch time (M2) only a **capability** recheck runs: gh-ost hard prerequisites — MySQL-family dialect, tool availability, channel session, target table exists with PK/UK. The recheck answers "can we execute", never "should we route" (thresholds/row counts/boundary matrix are NOT re-evaluated); results are not cached (what froze is the plan, not the environment). Failure → stmt FAILED + `RELEASE_ROUTE_CAPABILITY` event → the override channel, never a silent downgrade.
3. **DML_BATCH (ruling 3): staged — GHOST first, DML_BATCH blocked on the release chain.** M2 wires only the GHOST executor; a DML_BATCH segment is blocked before dispatch (stmt FAILED + `RELEASE_ROUTE_UNSUPPORTED` event; human exits: route override → explicit approved direct execution, or returnStmt back to the ticket chain where DML_BATCH capability is complete). The release-side segment adjudication surface (RERUN_BATCH/SKIP_BATCH, option-C failure semantics) and the DML_BATCH executor wiring (B8 binding generalization) are deferred to a dedicated follow-up task (parent observation pool **O-C7-1**). The B8 seam is not touched by this task.
4. **Override form (ruling 4): a new route-dedicated override**, built parallel to the C4 pattern: `dm_gov_route_override` table + `GOV_ROUTE_OVERRIDE` permission label + mandatory reason (≤1024) + expiry ≤7 days + single-use CAS consumption + HIGH audit + `RELEASE_ROUTE_OVERRIDE` event. Semantically isolated from `dm_gov_schema_gate_override` — the two overrides never substitute for each other (pinned).
5. **Incidental ruling: NO stock backfill** (E15 recommendation, mirroring ADR-011 Decision 5's stock precedent): existing/in-flight releases keep null-plan → legacy DIRECT byte-identical; only new merges carry a manifest.

Milestone discipline: **M1** carrier + freeze propagation (write-only — zero dispatch change) → **M2** segment-aware dispatch (`createReleaseStmtJob` reads the manifest: empty → legacy DIRECT byte-identical; non-empty → per-segment dispatch with AUTOEXEC stmtRange filtering + global-with-holes exec_order, GHOST executor via generalized binding, DML_BATCH blocked; capability recheck; sweep segment liveness; SUCCESS segments never replayed on retry) → **M3** plan-drift gate (order at all three dispatch points: hash(text) → plan(manifest) → precheck(B) → diff(A); `RELEASE_PLAN_DRIFT` NEVER overridable — integrity class, mirroring text-hash drift) + route override suite + frontend frozen-plan review surface. Rollback points: DROP TABLE + DROP COLUMN (M1, transparent — no reader) / dispatch branch reverts to null-plan legacy (M2, structural) / hash comparison reverts to text-only + override table deactivated (M3).

Red lines: no silent DIRECT downgrade for a planned stmt (code structure + events + tests, triple-pinned); binding generalization is additive and mutually exclusive with the ticket binding (ticket-chain writeback paths zero-diff); stock null-plan behavior byte-identical; no re-probe / no re-route; `executionKey` semantics unchanged; B8 seam / DmlBatch* / GhostAsyncTask untouched until M2's ruled scope; historical migrations never modified.

### Rejected alternatives

- **Option A (columns on `DmProdReleaseStmtDO`)**: invasive across the DO's 14 consumer surfaces (including the C4 gate engine that reads stmt rows); a single JSON column carrying multi-segment runtime state would import the ticket-side `exec_segments` parsing/concurrency/single-writer complexity into the release chain; per-segment hash pinning is less structured than row-level. The lone advantage (one fewer table) does not pay for the risk surface.
- **Third form (release references the source ticket's `precheck_result.segments` in place, no copy)**: breaks freeze semantics (ticket-side resubmit authoritatively recomputes `precheck_result` — a post-merge source change would pollute the frozen release plan, violating "approved manifest == executed set"); lifecycle mismatch (source rows mutate/vanish across return-revise while the release stmt's UK occupancy is independent); target-DB mismatch (a PRE_DDL plan was probed against PRE — referencing it directly applies pre-probed routing to prod with no recheck); and runtime state still needs a release-side carrier, making it half of option B anyway. Its sound core — copy a frozen snapshot at merge — is exactly what option B's propagate absorbs.
- **Prod-side re-probe / re-route (re-running `evaluateGhostRoute` at release dispatch)**: violates the freeze ruling ("全部冻结…按计划执行"); routing truth would diverge from the approved artifact; rejected by ruling 2 in favor of freeze + capability-only recheck.
- **Reusing `dm_gov_schema_gate_override` with an extended gate_type**: semantic pollution — a schema-gate override relieves "cannot prove safety" (infrastructure unknown / drift), a route override records "execution-shape risk explicitly accepted" (lock risk of a direct threshold-exceeding statement). Ruling 4 chose the parallel new table/label/event family; cross-substitution is pinned forbidden.
- **One-step release-side DML_BATCH adjudication surface** (RERUN_BATCH/SKIP_BATCH + option-C failure semantics + segment-level retry/resume/sweep in this task): the release chain has NONE of the segment-level recovery infrastructure the ticket-side option-C semantics depends on (`retryGroup` / `resumeGroupUnderLock` / heartbeat sweep); hasty wiring produces hanging states ("batch task terminal but nobody advances the release"). Ruling 3 staged it: block now with explicit human exits, full executor in the dedicated follow-up (O-C7-1).

## Consequences

- **M1 (delivered)**: new table + `plan_hash` column are WRITE-ONLY — no dispatch-path reader exists, execution behavior byte-identical; rollback = DROP TABLE + DROP COLUMN, transparent to older binaries. Merge write condition mirrors the ticket-side carrier: rows are written ONLY when the source plan carries ≥1 routed (GHOST ∨ DML_BATCH) segment; pure-normal groups / no plan / unparsable plan (parsePlan is never-throw) keep null-plan + `plan_hash` NULL. `plan_hash` rides the stmt INSERT; manifest rows follow post-insert (releaseStmtId known then). Cascade deletes mirror the schema table's four sites; resubmit re-propagates in the same transaction window BEFORE `createSqlTicket` (the C5 approval-round reset rides that call — ordering per design D2). `ReleasePlanHashUtils` is the single canonical implementation: seg_idx ascending, per-row plan-column join `segIdx|type|from|to|stmtIndex|table|rows|sql|batchKeyColumn|batchKeyType|idempotent` (null → empty, idempotent → 1/0/empty, sql_text as-is — no whitespace normalization: the pin compares manifest rows against themselves), rows joined with `\n`, SHA-256 lowercase hex (GovSqlHashUtils algorithm contract); runtime and identity columns never participate (M2 runtime mutation cannot invalidate the pin); empty → null.
- **M2 (pending)**: `createReleaseStmtJob` two-level decision (manifest → segment dispatch; NO DIRECT fallback branch for a planned stmt — "downgrade impossible" by construction); `GhostAsyncTask` binding generalization (additive `releaseStmtId`/`releaseId`, mutually exclusive with `ticketId`/`groupId`, ticket path zero-diff — the de-facto GHOST-side seam definition, written back to the ghost spec as O-C7-2 on delivery); release-side session economy (three `releaseSessionQuietly` mirrors, cap-2 slot discipline); `recoverReleaseCompletionIfDue` segment-level liveness extension; retry semantics — SUCCESS segments NEVER replay (option-C spirit), a FAILED segment resets to PENDING and the chain resumes at firstNonTerminal; two new events `RELEASE_ROUTE_UNSUPPORTED` / `RELEASE_ROUTE_CAPABILITY`.
- **M3 (pending)**: gate order at the three dispatch points extends to hash → plan → precheck → diff; `RELEASE_PLAN_DRIFT` (manifest recompute ≠ plan_hash, or plan_hash set but manifest empty) → stmt FAILED, never overridable; `dm_gov_route_override` + `GOV_ROUTE_OVERRIDE` (4-point registration discipline) + `GovRouteOverrideService` (CAS single-use) consumed at the two blocking sites (both convert the blocked segment to AUTOEXEC direct execution = risk explicitly accepted); frontend frozen-plan block + DML_BATCH blocking banner + override management + four new timeline event types.
- Spec: `governance-contracts.md` gains the manifest contract entry at M1; `ghost-online-ddl.md` release-side wiring and `lockfree-dml.md` §10 disclosure revisions land with M2/M3. Tests: `ReleaseSegmentPropagateTest` (M1, 14 pins — propagation mapping, write condition, four cascade deletes, resubmit re-freeze, plan_hash caliber); M2 adds `ReleaseSegmentDispatchTest`, M3 adds `GovRouteOverrideServiceTest` (design D12 authorization).
- Real-database functional verification (a release with a GHOST segment executing through gh-ost on the test environment) is deferred to the project-final unified integration test per the standing user ruling; the migration itself validates by compile + first-boot `dm_update_history` SUCCESS row.
