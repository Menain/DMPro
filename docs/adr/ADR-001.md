# ADR-001: Role/Group separation with materialized expansion and ledger-scoped revocation

**Status**: Accepted (implemented; correction-loop interaction refined in Phase 5)

**Date**: 2026-09-06 (spec rev.2); implemented Phase 2

## Context

CloudDM's existing permission model has two independent layers that never interconnect:

- **Role** (`dm_auth_role`): carries functional permission labels (`SecRoleAuthLabel` / `@RequestAuth`). A user with a role gets *what operations they can perform* — but no instance-level access.
- **Resource authorization** (`dm_auth_res`): per-user, per-datasource, path-scoped grants with validity periods. This is the *who can touch which database* layer.

READY_PLAN question 1 flagged "role authorization grants no instance access" as a defect. Code investigation confirmed it is **by design, not a bug**: the two layers are deliberately separate. The real gap is the *absence of any group entity* — authorization is strictly per-user, so granting a team access to a PRE database means writing N individual `dm_auth_res` rows and maintaining each independently.

The question is how to add group→resource authorization that takes effect globally across all existing authorization paths (console queries, instance browsing, ticket submission) without modifying those paths or the core `dm_auth_res` table structure.

## Decision

Adopt **D5: global materialized expansion into `dm_auth_res`** with four supporting design choices:

1. **Role=functional, Group=resource** — keep the two layers separate; groups are the resource-authorization analog of roles, not a generalization of roles. No group inheritance or ABAC in P0.

2. **Materialized expansion** — group resource × member combinations are written directly as `dm_auth_res` rows (`ownerUid=member`). All existing LIKE-existence auth checks see these rows with zero code change. The expansion is **not** runtime-computed via a UNION.

3. **"Always expand, each deletes its own"** — expansion bypasses `mergeGrantedAuth`'s label-merge logic (insert directly via `resMapper().insert()`). Expanded rows and direct-grant rows on the same key coexist without merging. Revocation deletes only the rows listed in the group's own ledger — never by path/key, never touching a direct grant.

4. **`res_desc` ownership marker + ledger table** — expanded rows carry `PERM_GROUP:<groupId>:<groupResourceId>` in the existing `res_desc` column (no new column on `dm_auth_res`). An independent ledger table `dm_perm_group_grant_record(group_id, group_resource_id, member_uid, auth_res_id)` tracks which expanded rows belong to which group resource, with `uk_grant_record(group_resource_id, member_uid)` as the duplicate guard. Individual revoke paths reject `PERM_GROUP:`-marked rows before mutating (touchpoint #4).

### Rejected alternatives

- **Runtime UNION expansion** (query-time join group members with group resources): deferred to P2+. Avoided in P0 because it requires rewriting every auth-check query path; materialized expansion achieves global effect with zero path changes. Recorded as a future option if expansion row count becomes problematic (risk #9: expansion data = members × resources).
- **`grant_source` column on `dm_auth_res`**: rejected because `dm_auth_res` is a core table with no extension columns and no source/remark fields; adding one is invasive. `res_desc` (display-only, never parsed by auth logic) is the existing free-text slot and suffices as the ownership marker.

## Consequences

**Positive**:
- All existing authorization paths (console query, instance browse, ticket creation) work with zero modification — expanded rows are ordinary `dm_auth_res` rows.
- Direct grants and group grants coexist safely; LIKE-existence checks are unaffected by duplicate rows on the same key.
- Independent revocation is guaranteed: group revocation deletes only ledger-listed rows, never a direct grant.
- Adding/removing members, granting/revoking resources, and group disable/enable all recompute expansions in the same transaction — "leave group = lose access" is achieved by the materialized mechanism.

**Negative / constraint**:
- Expansion row count = members × resources. For enterprise-internal scale this is acceptable; if it grows problematic, the runtime UNION approach (P2+) should be re-evaluated.
- Orphan ledger rows can accumulate when expanded rows are swept by the expiry cleaner (`deleteByEndTimeExceed`); they are purged on the next group recompute.
- The `res_desc` marker is display-only; any new code path that deletes/updates `dm_auth_res` on behalf of an individual user action must add the `assertNotPermGroupGranted` guard. System-level bulk paths (`clearAuthOfRes`, `clearAuthOfUser`, `deleteByEndTimeExceed`) intentionally remain unguarded.
