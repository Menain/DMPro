# ADR-005: Governance roles via env params (no dm_sys_env table change)

**Status**: Accepted (implemented as specified; no-UI-editor confirmed as intentional, not a gap)

**Date**: 2026-09-06 (spec rev.2); implemented Phases 1, 3

## Context

The governance layer needs to distinguish PRE environments from PROD environments to apply different policies (PRE = auto-advance + correction loop; PROD = mandatory approval + Guard + Preflight + no-skip). The existing environment model (`dm_sys_env`) has only `envName`/`description` — free-text labels with no DB unique constraint, no PRE/PROD enumeration, and no role semantics.

CODE_DESIGN proposed adding an `environment` enum column to a `resource_environment_binding` table. But `dm_sys_env` is a core table shared across the entire platform; adding a role column to it would couple platform infrastructure to governance semantics and require migrating existing environments.

## Decision

Adopt **env param KV mechanism for governance roles** — do not modify `dm_sys_env` table structure. Use the existing `dm_sys_env_param` KV store (env param keys) to add four governance keys:

| Key | Values | Semantics |
|---|---|---|
| `GOV_ROLE` | `PRE` / `PROD` / empty | PRE: ticket execution success → Revision freeze; failure → correction loop. PROD: mandatory approval (non-closable) + governance-only ticket acceptance + Guard/Preflight required + no-skip. Empty: fully preserve existing non-governance behavior. |
| `GOV_DML_DIRECT` | on/off (default off) | Path B direct-PROD-DML entry switch (meaningful only for PROD-role environments). |
| `GOV_DML_ROW_LIMIT` | `warn:N,block:M` | Path B EXPLAIN row-count threshold tiering: ≤warn normal; warn~block HIGH risk on approval form; >block reject. |
| `GOV_AUTO_CONFIRM` | on/off (default off) | Auto-confirm execution after approval (D12; auto path still passes Guard+Preflight). |

The `GOV_ROLE` tag provides **per-environment gray-release capability**: governance applies only to environments with a role tag. Libraries can be onboarded one at a time; untagged environments are completely unaffected (existing ticket behavior, zero change).

### Rejected alternatives

- **`environment` enum column on `dm_sys_env` or a binding table**: rejected because it modifies a core platform table, couples infrastructure to governance, and requires migrating existing free-text environments. Env params are the existing, zero-structure-change extension mechanism.

## Consequences

**Positive**:
- `dm_sys_env` table is untouched; no migration risk.
- Per-environment gray release is a natural consequence: tag one environment PRE/PROD, governance applies only there; untagged = zero impact (hard regression criterion, AC5).
- Env-id references (not env-name) immunize governance bindings against the existing `env_name` no-unique-constraint defect (risk #4).

**Negative / constraint**:
- **No frontend editor for GOV_* params** (by design, confirmed in Phase 12): the configuration front door is `POST /api/entry/envparam/bindEnvParam` (label `DM_DS_MANAGE`). The logicalDb page shows `govRole`/`govDmlDirect` read-only; `BindingSetFO` carries no GOV_* fields. A dedicated UI editor is a registered P1 improvement candidate, not a gap.
- `bindingSet` must pre-check that no two envs in the new set carry the same non-empty `GOV_ROLE` — `UNIQUE(logical_db_id, env_id)` only guarantees one target per env, not per role. Conflicts are rejected at configuration time to keep `getBinding` deterministic.
- `getBinding` three-state error semantics are load-bearing (callers rely on them): 0 matches → business exception; >1 matches → business exception listing conflicting envIds (determinism over convenience, never silently pick first); db disabled/wrong-tenant → business exception.
